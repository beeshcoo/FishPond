# 需求追溯矩阵 (Traceability)

> 放在 `<项目>/.fishpond/TRACEABILITY.md`。大型项目"零需求遗漏"的抓手：
> **每条需求都能一路追到卡片 → 测试 → 证据；任何一格空着，就是缺陷逃逸的口子。**

## 状态图例
`待开发` · `开发中` · `测试中` · `已交付` · `已上线`

| 需求ID | 需求描述 | Epic/Feature | 模块卡片 | 自动化测试(文件::用例) | 证据(输出/PR/截图) | 状态 | 备注 |
|---|---|---|---|---|---|---|---|
| REQ-001 | <一句话需求> | <所属> | cards/xxx.md | tests/xxx::case_a, case_b | <CI 链接/输出片段> | 待开发 | |
| REQ-002 | | | | | | | |

## 使用规则
```
1. 需求一确认就登记(先占 ID)，不等开发。
2. 卡片/测试/证据随开发推进逐格填实；DoD 第 6 项要求填齐才算完。
3. 交付评审时逐行核对：有没有需求只有描述、没有测试或证据？有 = 不许交付。
4. 需求变更 → 改这里 + 改卡片 + 改架构(若涉及)，三处同步。
```

## 覆盖自检（每次交付前回答）
```
☐ 是否每条"已交付/已上线"的需求都有真实跑绿的测试与证据？
☐ 是否存在"已上线"但矩阵里查不到的功能（= 影子功能，未追溯）？
☐ 是否存在"待开发"却被当成已完成对外承诺的需求？
```
